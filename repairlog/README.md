# Опять работа?

Веб-приложение для учёта ремонтов кухонного, бытового, промышленного и
ресторанного оборудования. Подробный план разработки — в корневом
документе плана проекта.

## Стек

Django 5, PostgreSQL 16, Django Templates + HTMX + Bootstrap 5, Docker Compose.

## Попробовать без компьютера (Render, бесплатно)

`render.yaml` в корне репозитория — Blueprint для one-click деплоя на
[Render](https://render.com), весь процесс через браузер (включая
телефонный), без Docker и терминала:

1. Откройте
   <https://render.com/deploy?repo=https://github.com/shansk3d-ux/Shest-works>,
   войдите (можно через GitHub) и подтвердите создание — Render сам поднимет
   веб-сервис и бесплатную PostgreSQL по `render.yaml`.
2. Дождитесь окончания первого деплоя (несколько минут) — при старте
   контейнер сам применяет миграции, наполняет справочники и создаёт
   демо-пользователя (`manage.py bootstrap_demo`).
3. Откройте выданный Render адрес (`https://opyat-rabota-XXXX.onrender.com`),
   войдите под `demo` / `opyat-rabota-demo`.

**Это публичный бесплатный демо-стенд, не для реальных данных:**
логин/пароль общие и лежат прямо в `render.yaml`, любой, кто найдёт адрес,
может зайти. Бесплатный веб-сервис Render использует временный диск —
загруженные фото ремонта пропадут при перезапуске/передеплое; бесплатная
БД Render ограничена по времени жизни. Для настоящей эксплуатации —
`docker-compose.prod.yml` на своём сервере (см. «Деплой» ниже).

## Запуск локально (Docker)

1. Скопируйте `.env.example` в `.env` и при необходимости отредактируйте значения:

   ```bash
   cp .env.example .env
   ```

2. Соберите и запустите контейнеры:

   ```bash
   docker compose up --build
   ```

3. Примените миграции и создайте суперпользователя (в отдельном терминале):

   ```bash
   docker compose exec web python manage.py migrate
   docker compose exec web python manage.py createsuperuser
   ```

4. Откройте <http://localhost:8000/> — должна открыться стартовая страница Опять работа?.

5. Заполните справочники начальными данными (типы оборудования, категории,
   популярные бренды):

   ```bash
   docker compose exec web python manage.py seed
   ```

## Задачи и уведомления

Раздел «Задачи» (`/tasks/`) отделён от заявок на ремонт, но задачу можно
опционально привязать к заявке из списка. У задачи есть название,
описание, дата/время и три действия: «Завершить», «Отложить» (открывает
поле «Отложить до» с датой и временем) и «Отменить».

Пока открыта вкладка приложения в браузере, JS раз в минуту опрашивает
`/tasks/due/` и для наступивших задач показывает браузерное уведомление
(нужно разрешение Notification API) и проигрывает звук — на выбор
«Стандартный», «Колокольчик», «Перезвон» или «Тревога» (файлы в
`static/sounds/`). Уведомление по каждой задаче отправляется один раз;
при откладывании задачи флаг отправки сбрасывается автоматически.

## PWA (установка на телефон)

Приложение — PWA: манифест `static/manifest.json` (имя, иконки 192/512px,
`display: standalone`) и минимальный service worker (`/service-worker.js`,
шаблон `templates/service-worker.js`, отдаётся Django-view'ой с корневым
scope, а не из-под `/static/`, — иначе браузер не даст ему контролировать
весь сайт). В Chrome на Android это даёт «Добавить на главный экран» —
приложение открывается как отдельное окно, без адресной строки браузера,
со своей иконкой.

Service worker кэширует **только статику** (лого, иконки) — HTML-страницы,
формы и все запросы к данным всегда идут в сеть напрямую. Это осознанно:
в системе учёта ремонтов нельзя показывать мастеру устаревшие из кэша
данные о заявках, только реальное состояние с сервера.

## Поиск

Глобальный поиск (`/search/`, строка поиска в шапке) ищет по симптомам,
диагнозам и выполненным работам заявок, а также по базе знаний (симптом,
причина, решение), используя полнотекстовый поиск PostgreSQL
(`SearchVector`/`SearchRank`, конфигурация `russian`) плюс точное
совпадение по коду ошибки. Работает только на PostgreSQL — на SQLite
(дефолт `DATABASE_URL` для быстрой локальной разработки без БД) поиск
вызовет ошибку, для него нужна реальная PostgreSQL, как в
`docker-compose.yml`.

## Деплой

Продакшен-стек: Gunicorn (Django) + Caddy (реверс-прокси и автоматический
HTTPS по протоколу ACME) + PostgreSQL, всё в `docker-compose.prod.yml`.

1. На сервере укажите DNS-запись домена на его IP и откройте порты 80/443
   (нужны Caddy для выпуска сертификата Let's Encrypt).

2. Скопируйте `.env.example` в `.env` и заполните для продакшена:

   ```bash
   cp .env.example .env
   ```

   Обязательно замените: `DEBUG=False`, `SECRET_KEY` — на случайную
   строку, `ALLOWED_HOSTS` и `CSRF_TRUSTED_ORIGINS` — на реальный домен
   (`CSRF_TRUSTED_ORIGINS=https://ваш-домен`), `POSTGRES_PASSWORD` — на
   надёжный пароль, `DOMAIN` — на домен для Caddy. `SECURE_SSL_REDIRECT`
   уже включён по умолчанию в `config/settings/prod.py`.

3. Соберите и запустите:

   ```bash
   docker compose -f docker-compose.prod.yml up -d --build
   ```

   При старте контейнер `web` сам применяет миграции и собирает
   статику (`deploy/entrypoint.sh`) перед запуском Gunicorn; Caddy
   раздаёт `staticfiles/` и `media/` напрямую и проксирует остальные
   запросы на Gunicorn.

4. Создайте суперпользователя и заполните справочники:

   ```bash
   docker compose -f docker-compose.prod.yml exec web python manage.py createsuperuser
   docker compose -f docker-compose.prod.yml exec web python manage.py seed
   ```

5. Включайте `SECURE_HSTS_SECONDS` (например, `604800` — неделя) только
   после того как убедитесь, что HTTPS стабильно работает: HSTS запрещает
   браузеру обращаться к сайту по HTTP на указанный срок.

## Бэкапы

`deploy/backup.sh` делает дамп базы (`pg_dump --clean --if-exists`, чтобы
дамп сам сносил старые объекты при восстановлении) и архив `media/`,
кладёт их в `backups/` рядом с проектом и удаляет файлы старше 14 дней
(`RETENTION_DAYS`, переменная окружения). Запускается против уже
поднятого `docker-compose.prod.yml`.

Ежедневный запуск — через cron на сервере (не в контейнере, чтобы
бэкапы переживали пересоздание контейнеров):

```bash
crontab -e
# добавить строку (бэкап каждый день в 03:00):
0 3 * * * cd /путь/к/repairlog && ./deploy/backup.sh >> /var/log/repairlog-backup.log 2>&1
```

Бэкапы `backups/` лежат на том же сервере — этого достаточно от
человеческой ошибки или сбоя контейнера, но не от потери самого сервера.
Периодически копируйте `backups/` в другое место (объектное хранилище,
другой сервер и т.п.).

### Восстановление

`deploy/restore.sh` — деструктивная операция: останавливает `web`,
затирает текущую БД дампом и (если передан вторым аргументом архив)
полностью заменяет содержимое `media/`. Требует явного подтверждения.

```bash
./deploy/restore.sh backups/db-20260101-030000.sql.gz backups/media-20260101-030000.tar.gz
```

Без второго аргумента восстанавливается только база данных.
